# Краткое описание промптов и принятых решений

Полный текст промптов — в `src/prompts/productCard.ts`. Здесь — краткая версия для
сопроводительного сообщения и проверки задания.

## 1. Как устроен промпт

Используются три части:

1. **System prompt** — роль и жёсткие правила.
2. **User prompt** — JSON товара между маркерами `<<<PRODUCT_JSON>>>` и
   `<<<END_PRODUCT_JSON>>>`, плюс автоматически найденные пропуски.
3. **Repair prompt** — предыдущий ответ и конкретный список нарушений; отправляется
   не более одного раза.

### Роль и аудитория

Модель выступает как старший технический контент-редактор B2B-каталога КИПиА.
Текст пишется для инженера-снабженца и контент-менеджера, а не для конечного
потребителя.

### Ключевые ограничения в промпте

- **Один источник фактов.** Единственный источник — JSON `INPUT`. Всё, чего там нет,
  считается неизвестным.
- **Запрет на домысливание.** Нельзя добавлять материалы, IP, класс точности,
  сертификаты, поверку, гарантию, страну производства, совместимость, интерфейсы,
  температурные диапазоны, преимущества и области применения.
- **Дословные значения.** Не пересчитывать единицы, не округлять, не менять диапазоны.
  Сохранять написание `МПа`, `G1/2`, `IP20`, `DM 02`, `°C`.
- **Пропуски.** Для отсутствующей характеристики — ровно `«данных нет»`. Такие поля
  перечисляются в `missingData`.
- **Заголовок.** Не более 70 символов, одна строка, без кавычек и Markdown. Включает
  название/модель, производителя и 1–2 параметра из входа.
- **Описание.** 800–1200 символов с пробелами; целевой объём 900–1100, чтобы не
  попадать ровно на границу. Без Markdown, HTML, списков и эмодзи.
- **Поисковые запросы.** 3–5 штук, строчными буквами, без кавычек, только на основе
  названия, модели, производителя и характеристик.
- **Commercial-блок.** Кому подходит и какие задачи решает — только по входу. Если
  данных мало, прямо писать «Требует уточнения: ...».
- **Формат ответа.** Только валидный JSON по схеме, без текста вокруг.

### Структурированный вывод

Запрос идёт с `responseMimeType: application/json` и `responseJsonSchema`. Схема
фиксирует поля `seoTitle`, `seoDescription`, `keySpecs`, `searchQueries`,
`commercialBlock`, `missingData`. Температура — `0.3`: достаточно вариативности, но
меньше риска «додумывания».

### Repair-проход

Если ответ нарушает длины, количество запросов или содержит значение не из входа,
сервис делает один повторный запрос. В нём есть исходный JSON, предыдущий ответ и
перечень конкретных проблем. Промпт запрещает добавлять новые факты и просит расширять
описание только пересказом уже имеющихся данных. Одна попытка — сознательное
ограничение стоимости и времени.

## 2. Принятые решения

1. **TypeScript + Express + ванильный UI.** Без React и сборщика: прототип проще
   запустить, меньше зависимостей и меньше риска, что проверяющий потратит время на
   инфраструктуру.
2. **Прямой REST-вызов Gemini через `fetch`, без SDK.** Меньше зависимостей, прозрачнее
   обработка HTTP-кодов, таймаутов и повторов.
3. **Zod на входе.** Явно проверяются типы, пустые поля и размер тела запроса; ошибки
   возвращаются с путём до проблемного поля.
4. **JSON Schema на выходе.** Модель не может вернуть произвольную структуру, а
   невалидный JSON отлавливается до бизнес-логики.
5. **Детерминированная пост-проверка `reconcileDraft`.** Это главный барьер от
   галлюцинаций:
   - значение из `keySpecs` должно встречаться во входе дословно, иначе заменяется на
     `«данных нет»`;
   - восстанавливается исходный регистр и написание обозначений;
   - все характеристики из `specs` гарантированно попадают в результат;
   - слишком длинные заголовок и описание обрезаются;
   - слишком короткое описание дополняется безопасными оговорками без новых фактов;
   - дубликаты в `missingData` и запросах убираются;
   - при нехватке запросов добавляются шаблонные, но не выдумывающие свойства.
6. **Пропуски считает код, а не модель.** `missingFields` формируются при нормализации
   входа: нет производителя, характеристик, описания или описание слишком короткое.
   Это не зависит от галлюцинаций LLM.
7. **Ключ только в окружении.** Поддерживаются `GEMINI_API_KEY` и `GOOGLE_API_KEY`;
   `.env` в `.gitignore`, в браузер ключ не попадает.
8. **Понятные ошибки API.** Невалидный JSON — 400, пустые поля — 400, таймаут — 504,
   блокировка safety — 422, ошибка Gemini — 502. Для 408/429/5xx есть повторы с
   задержкой.
9. **Mock-провайдер только для офлайна.** Он позволяет проверить UI, CLI и тесты без
   ключа, но не подменяет реальную модель в примерах.
10. **Один товар за запрос.** Для прототипа достаточно; batch, очередь и кэш описаны в
    ограничениях.

## 3. С какими сложностями столкнулись

- **`gemini-3.8-flash` возвращал HTTP 503 «high demand».** Модель осталась значением по
  умолчанию, а примеры собраны на доступной `gemini-3.5-flash-lite`; команда и причина
  указаны в `README.md` и `examples/README.md`.
- **Модель склонна писать описание короче 800 символов.** В промпте задан целевой
  диапазон 900–1100, а код детерминированно дополняет короткий текст безопасными
  оговорками без технических фактов.
- **Модель меняет регистр и формат обозначений.** Пост-проверка возвращает написание из
  входа: `МПа`, `G1/2`, `DM 02`, `IP20`.
- **Риск выдать пропуск за факт.** Для неизвестных характеристик разрешено только
  `«данных нет»`; такие значения явно отделены от подтверждённых.
- **Второй товар был в XML, а не в JSON.** Он преобразован в JSON, а технические
  характеристики дополнены только со страницы товара, указанной в XML; источник описан
  в `samples/README.md`.

## 4. Что сознательно не проверяется автоматически

- Коммерческие формулировки и SEO-описание проверяются на длины, но не на каждое
  утверждение по смыслу. Перед публикацией нужна вычитка человеком.
- Частотность и конкуренция поисковых запросов не измеряются.
- Нет сравнения с эталонными карточками и A/B-тестов.

Эти ограничения перечислены в разделе «Ограничения и что можно улучшить» в `README.md`.
